Sure, an agent 40 turns into a real job. It has read 9 files, run a dozen commands, hit 2 dead ends, and recovered from both. And on turn 41, it asks you the question you already answered on turn 4.

Here's why: Between turns, an agent remembers nothing. The loop around it compensates by pasting the entire history back into the prompt, every single turn. And on one public benchmark run, a single session of 200 questions burned through 221 million tokens, doing exactly that.

The obvious fix is the one the big labs sell: a bigger context window. Except there's now well-known research measuring what actually happens as input grows, across 18 frontier models. And the finding is uncomfortable: Accuracy starts falling long before the window is full. More room doesn't fix the problem. More room is the problem.

Why your agent is a goldfish with a filing cabinet. Strip the mystique off: An agent is a model, which remembers nothing between calls, plus a loop that keeps handing it the transcript. That's it. Between sessions, your agent is a new hire who read the handover note, and nothing else.

So the loop hoards every file it read, every command output, every stack trace—all of it pasted back in, every turn. The costs compound in two directions at once.

The first is money and time, and it's brutal at scale. On a 50-task software engineering session, this project's own baseline measurement is over 3 billion tokens for one benchmark.

The second is the one people miss: All that text makes the model worse. The context rot research is clear on this: Models given growing input degrade at tasks a child could do, some by 30% to 50%, and the degradation starts well below the advertised window size. The number on the box is not the number you get.

So the hoarding strategy fails on cost and accuracy simultaneously, which sets up the strange thesis of this project: The way to make an agent smarter is to help it remember less, as long as you're extremely careful about what 'less' means. And a 50-year-old psychology result says that's exactly how the only working example we have does it.

The psychology: Two minutes that make the architecture obvious. In 1972, the psychologist Endel Tulving—Tulving split human memory in two: Episodic memory, the events you lived through with time attached; semantic memory, the facts you know with the event that taught you them stripped away. You know Paris is the capital of France; you have no idea which afternoon you learned it.

The interesting part is the arrow between them. Episodes get replayed, patterns get extracted, the episode itself fades. Psychologists call it consolidation, and it's not just a theory. Replay during sleep is a mechanism neuroscience has actually observed. And the other half was measured all the way back in 1885: Without review, most of what you learn today is gone within days. Forgetting isn't the bug in that system; forgetting is the compression step.

Hold that: Raw experience at the bottom, distilled knowledge at the top, and a working path between them. Now watch how closely this repository follows it. Idea one: The task you're in right now—symbolic short-term memory.

In a long task, the token hogs aren't your instructions. They're the intermediate logs: Search results, file dumps, stack traces. Here's what this plugin does with them, and I'm describing the mechanism as documented and configured in the source:

Full tool outputs get moved out of the prompt entirely, written to Markdown files on disk. What stays in context is a diagram, a Mermaid graph of what happened. Mermaid is that little text syntax from GitHub READMEs: Boxes and arrows as plain lines. Hundreds of thousands of tokens of log collapse into a few hundred tokens of shape.

And the crucial design decision: Every node in that diagram carries an ID pointing back to the raw file. When the agent hits an error and needs the actual stack trace, it fetches by ID, and the full text comes back. That's the constraint that makes this different from summarization. A summary is one-way—the detail is gone. This is a folded map you can open again.

Now, the verified numbers from the configuration itself. Compression is threshold-driven: At 50% of the context window, it compresses mildly; at 85%, aggressively. Both are right there as defaults in the config file. The diagram itself is capped at 20% of the token budget, with a 4,000-character ceiling on the canvas. So the map can never eat the room it's saving. Those are exactly the kinds of numbers that separate an engineered system from a demo, and they're all inspectable.

Idea two: What your agent knows about you—the four-layer pyramid. The long-term side is Tulving's arrow written as four layers:

L0 is the raw conversation: Everything, exactly as said. L1 extracts atoms: A fact, a preference, a constraint. L2 groups atoms into scenes: This project, this recurring kind of task. L3 is the persona: Your habits, your conventions, your defaults.

And here's a verified detail I love: The persona is rebuilt, regenerated from scratch, every 50 new memories. That's in the config as a default. Your profile isn't an append-only pile; it's periodically re-distilled, which is consolidation, literally implemented.

Recall runs the pyramid top-down: Persona first, because it's cheap and usually enough, down to atoms when a specific fact matters, all the way to the raw conversation only when exact wording counts. The vendor's benchmark for this half is a multi-session test where a user's preferences change over time—the nasty case—and their reported number is a jump from 48% to 76%.

The shape of the whole thing: Top to bottom, structure in context, evidence on disk, and a deterministic path between them. Their own documentation states it as a principle: 'Lower layers preserve evidence. Upper layers preserve structure.' And it's the best one-sentence summary of where all serious memory work is converging.

The headline, on a wide-search benchmark: 200 questions that are individually easy, but must all be right—exactly the shape that floods a context window. The plumbing, and why it passes the ownership test. Here's the part that made me take this seriously—verified from the source.

Where this is going: Memory stops being a cache and becomes an asset. There's a version-two direction in this repository that I think is the actual story, and it is bigger than token savings. The first generation of this system—everything we've covered so far—treats memory as a private cache: Your agent, your sessions, your profile. The newer direction reshapes memory into four kinds of shared asset, and the names tell you everything: Chat memory, skills, a wiki, and a code graph.

Take them in turn, because each one maps to something we've covered on this channel. Skills here are not prompt snippets. The repository itself ships skill definition files—I found them in the source tree—and the format carries versions, resources, trigger boundaries, execution steps, validation rules. That's closer to a package than a note. And regular viewers will recognize the shape immediately: It's the same skills format we spent a whole video on this week, now being generated from the agent's own successful runs. Think about that loop for a second: The agent does a task well, the system distills the winning procedure into a versioned skill, and the skill becomes reusable. That's the layering idea applied to actions: Raw execution traces at the bottom, common patterns in the middle, a distilled standard procedure at the top.

The wiki is the idea a well-known researcher floated earlier this year: Markdown entity pages that an agent writes and maintains, linked to each other, so knowledge compounds between sessions instead of evaporating. The code graph indexes how a codebase actually connects, so an agent starts a task already knowing the structure instead of rediscovering it—which, if you remember the token arithmetic from the top of this video, is precisely the rediscovery that was costing billions of tokens.

And the feature that matters most if you already have a codebase: The cold-start path. Point the system at an existing repository, a folder of documentation, or your old agent sessions, and it backfills the graph, the wiki, and the skills before your new agent has done a single thing. That flips the adoption economics. Memory systems normally have a cold-start problem: They're useless until they've watched you for weeks. Backfilling from artifacts you already own means day one starts warm.

One more design decision worth naming, because it's the responsible one: These shared assets carry owners, versions, and permissions—private by default, shared with a team only after review. Whether that review step is used well is up to the teams deploying it, but the fact that sharing an agent-generated skill requires a human gate is exactly the supply chain lesson from our skills video, learned in advance rather than after an incident.

Add it up, and you can see what memory is becoming in this design: Not a log, not a cache—an artifact with a license plate: Owned, versioned, permissioned, transferable in principle. Hold 'in principle,' because the closing section of this video is about the gap between that and transferable in practice.

Two problems nobody puts in the headline. Problem one: The caching bill—and I'm going to derive this rather than assert it. Every serious API provider discounts repeated prompt prefixes. Identical opening tokens get cached and billed at a fraction of the price. Now think about what memory injection does: It writes recalled memories into the front of your prompt, and the recall changes as the conversation moves. A shifting prefix means the cache stops hitting, which means some fraction of your token savings walks back out the door as full-price tokens. How much depends entirely on your provider's discount and your recall churn, and it's the first thing I'd measure in any deployment, because it's the difference between the headline saving and your actual bill. The general fix is known: Keep the injected block as stable as possible, put volatile recall later in the prompt. And where this project lands on that is worth checking in its tracker before you deploy at scale. This is exactly the kind of cost that never appears in a benchmark table, because benchmarks don't have billing accounts.

Problem two—and I think this is the more important one: Memory is an attack surface. We did a whole section this week on why installable agent skills deserve supply chain caution. Memory is the same problem, quieter. Anything your agent reads can now try to write itself into what your agent permanently believes. A malicious string in a scraped page or a poisoned document doesn't have to win in the current session anymore. If it gets extracted as an atom and consolidated into a scene, it's waiting for you next week, with the provenance fading at exactly the rate the architecture is designed to fade it. To this project's credit, the layered design helps here. There's a deterministic path from any distilled memory back to the raw conversation that produced it. So poisoning is auditable in a way flat vector stores aren't. But auditable in principle only matters if you occasionally audit. The personas and scenes are Markdown files. Read your agent's diary once in a while. Two minutes, and you'll either find nothing or something genuinely worth finding.
