## CO OCENIAMY
Repo: **Tencent/TencentDB-Agent-Memory** (MIT, ~7800 gwiazdek, maj 2026). W pelni lokalny system pamieci dla agentow AI (zero external API domyslnie).
Zrodla: film YT (autor pobral kod, sprawdzil configi i arytmetyke tabeli — mowi ze "wiekszosc sie zgadza, JEDNA linia w tabeli benchmarku NIE") + README repo + artykuly (marktechpost, medium).

### Architektura (z README + artykulow)
- **Pamiec KROTKOTRWALA (biezace zadanie), symboliczna:** pelne outputy narzedzi -> pliki `refs/*.md` (offload z okna kontekstu); stan zadania zakodowany jako **graf MERMAID** (kilkaset tokenow) trzymany w kontekscie; agent rozumuje po grafie, a gdy potrzebuje szczegolu -> drill-down po `node_id` do surowego pliku. 3 warstwy: `refs/*.md` (surowe) -> `jsonl` (step summaries) -> Mermaid canvas (top). Progi z filmu: 50% okna = kompresja lagodna, 85% = agresywna; graf capped 20% budzetu, 4000 znakow.
- **Pamiec DLUGOTERMINOWA (co agent wie o userze), warstwowa:** piramida semantyczna 4-poziomowa **L0 Conversation** (surowy dialog) -> **L1 Atom** (fakty atomowe) -> **L2 Scenario** (bloki scen) -> **L3 Persona** (profil usera). Drill-down po `node_id`/`result_ref` zamiast plaskiego vector recall. Deklaruja pelna sledzsalnosc i bezstratne odtworzenie (deterministyczna sciezka od abstrakcji do surowego dowodu).
- **Retrieval:** hybrydowy BM25 + vector + RRF. Domyslnie lokalny **SQLite + sqlite-vec** (bez zewnetrznej bazy). Opcjonalny Tencent Cloud Vector DB.
- **Wyniki (integracja z OpenClaw):** WideSearch pass 33%->50% przy -61.38% tokenow; SWE-bench 58.4%->64.2%; AA-LCR 44.0%->47.5%; PersonaMem accuracy 48%->76%.
- **Stack/dystrybucja:** npm plugin dla OpenClaw ORAZ **obraz Docker dla HERMES** (lub instalacja manualna).

## GŁOS ZENKA — OCENA KONTROLNA

### POTWIERDZONE

Wyłącznie na podstawie materiału przekazanego w zadaniu, bez niezależnej kontroli repozytorium:

- Obecny system fabryki jest już pamięcią lokalną opartą na plikach: „`wiedza/` (dokumenty), INDEX/destylaty, teleport, dzienniki”.
- TencentDB ma podobną filozofię, ale dodaje hierarchiczne streszczenia, identyfikatory węzłów i możliwość zejścia do materiału źródłowego.
- Materiał deklaruje lokalny backend „SQLite + sqlite-vec” oraz dystrybucję dla HERMES.
- Źródła nie są w pełni zgodne: autor filmu twierdzi, że „JEDNA linia w tabeli benchmarku” się nie zgadza.

Nie potwierdzam stanu kodu, issues, licencji, aktualności obrazu HERMES ani benchmarków, ponieważ Tomasz zabronił uruchamiania narzędzi i kontroli źródeł.

### ODPOWIEDZI

1. **Mermaid + node_id: TAK, warto podpatrzeć.**

Najcenniejszy jest nie sam Mermaid, lecz model:

`krótki stan zadania → identyfikator węzła → surowy dowód na dysku`.

To może ograniczyć wklejanie wielkich logów i pomóc po kompakcji. Nie gwarantuje jednak rozwiązania problemu: graf również może utracić ważny fakt, jeśli jego aktualizacja lub streszczenie będą błędne. Surowe dane muszą pozostać dostępne, a każdy węzeł powinien wskazywać konkretny plik i zakres.

**Werdykt pytania 1: TAK — najpierw mały prototyp rodzimego mechanizmu, bez TencentDB.**

2. **Piramida L0→L3: częściowo już to mamy.**

Przybliżone odpowiedniki:

- L0 Conversation → dzienniki i teleporty,
- L1 Atom → pojedyncze ustalenia w `wiedza/`,
- L2 Scenario → dokumenty tematyczne i destylaty,
- L3 Persona → zasady działania, karty środowisk i wiedza o Tomaszu.

Potencjalny zysk TencentDB to bardziej regularna struktura, automatyczny retrieval oraz jawna ścieżka od wniosku do surowego dialogu. Nasz system ma natomiast ważną przewagę: próg dowodowy i odpowiedzialność Klaudka za wpis. Automatyczna piramida mogłaby zamienić niezweryfikowaną wypowiedź w pozornie trwały „fakt”.

**Werdykt pytania 2: NIE wdrażać teraz całej piramidy. Podpatrzeć identyfikatory, relacje i ślad źródłowy.**

3. **Integracja z HERMES: technicznie możliwa według opisu, ale nieudowodniona w naszym środowisku.**

„Docker dla HERMES” nie oznacza automatycznie zgodności z używanym przez nas poleceniem `hermes -z`, istniejącymi katalogami, modelem sesji ani sposobem przekazywania teleportów. Kontener może być kompletnym środowiskiem demonstracyjnym, a nie pluginem możliwym do prostego dołożenia Heniosiowi.

**Werdykt pytania 3: teraz NIE WPINAĆ. Najpierw kontrola dokumentacji, kodu integracji, issues i izolowany test odtwarzalny.**

4. **Koszt infrastruktury wygląda niski; koszt złożoności i błędnej pamięci może być wysoki.**

SQLite jest rozsądnym wyborem lokalnym. Ryzyka leżą gdzie indziej:

- automatyczne streszczenie może zgubić warunek lub źródło,
- baza może stać się drugim, konkurencyjnym fundamentem obok `wiedza/`,
- migracje schematu i zmiany świeżego projektu mogą utrudnić utrzymanie,
- retrieval może zwracać trafne językowo, ale nieaktualne albo niepotwierdzone informacje.

Niezgodność jednej linii benchmarku należy potraktować poważnie jako sygnał ostrzegawczy, ale nie jako dowód dyskwalifikujący cały projekt. Odbiera ona prawo do powtarzania liczb marketingowych bez reprodukcji. Wyniki procentowe z zadania traktuję jako deklaracje, nie fakty.

**Dojrzałości oraz sytuacji w issues: NIE WIEM.**

### HIPOTEZY

Najlepsza droga kosztowa to wdrożenie samego wzorca krótkotrwałego w obecnym systemie:

1. Każdy duży output zapisywany do pliku.
2. Krótki rejestr węzłów: `node_id`, opis, status, źródło, zależności.
3. Mały „canvas” bieżącego zadania, generowany z rejestru.
4. Kontrola, czy każdy węzeł prowadzi do istniejącego surowego materiału.
5. Test na jednej długiej sesji: czy po kompakcji można poprawnie odtworzyć decyzje i dowody.

Mermaid może być formatem prezentacji, ale dane kanoniczne lepiej trzymać w prostym JSONL lub Markdown. Diagram jest dobry dla człowieka i modelu, lecz słabszy jako jedyne źródło stanu.

Długoterminową pamięć warto rozważać dopiero po powodzeniu krótkoterminowego prototypu. To ona niesie większe ryzyko utrwalania błędów i konfliktu z zasadą, że do `wiedza/` trafiają wyłącznie rzeczy sprawdzone.
